# ForTunCloud 하네스 운영

파일별 역할, 작성 이유와 실제 검증 결과는 [구성 보고서](IMPLEMENTATION_REPORT.md)를 참고한다.

## 목적과 구성

기존 코드를 유지하면서 AI의 탐색·구현·협업·검증을 반복 가능한 절차로 만든다.
백엔드는 현재 한 서버의 모듈 구조를 유지하고, 향후 부하에 따라 분리할 수 있도록 경계를 지킨다.

| 파일 | 역할 | 이유 |
| --- | --- | --- |
| `../AGENTS.md` | 메인의 분류·위임·통합 규칙 | 작은 변경에도 두 에이전트가 실행되는 낭비 방지 |
| `../.codex/config.toml` | 서브에이전트 동시 실행 상한 2 | 백엔드·프런트 담당만 필요 시 실행 |
| `../.codex/agents/backend.toml` | 선택적인 백엔드 보조 에이전트 | 메인과 분리한 독립 보조 범위에만 사용 |
| `../.codex/agents/frontend.toml` | 프런트 커스텀 에이전트 | 독립 작업과 계약 기반 협업 |
| 각 저장소의 `AGENTS.md` | 저장소별 짧은 상시 지침 | 단독 체크아웃에서도 구조·스타일 유지 |
| `TASK_TEMPLATE.md` | 최소 위임 정보 | 전체 대화 전달과 반복 탐색 감소 |
| `API_CONTRACT_TEMPLATE.md` | 양쪽이 공유하는 HTTP 계약 | 필드·오류·null 해석 차이 방지 |
| 백엔드 `docs/harness/ARCHITECTURE.md` | 계층 경계와 서버 분리 기준 | 기존 예외와 신규 규칙 구분 |
| 각 저장소의 `docs/harness/TESTING.md` | 검증 범위와 환경 제약 | 환경 실패를 코드 성공으로 오인하지 않음 |
| 각 저장소의 `scripts/verify.ps1` | 실패 시 즉시 중단하는 검증 진입점 | 마지막 명령 성공이 앞선 실패를 가리지 않음 |
| 백엔드 `.agents/skills/forjun-maintenance/SKILL.md` | 유지보수·기능 개선 시 영향 분석과 선택 검증 | 관련 백엔드 테스트를 기본으로 하고 필요한 흐름만 E2E 수행 |

## 작업 분류

1. 메인은 요청을 backend / frontend / contract / unknown으로 분류한다.
2. 메인은 백엔드 개발·검증을 기본 담당한다. 작은 프런트 수정도 직접 처리하고, 큰 독립 프런트 작업만 프런트 담당에게 위임한다.
3. unknown은 메인이 먼저 재현·진단한다. 백엔드 보조는 사용자 요청 또는 명시적으로 분리한 독립 보조 작업에만 사용하고 중복 조사하지 않는다.
4. contract 작업은 메인이 API 계약을 작성하고 양쪽에 같은 버전을 전달한다.
5. 계약이 확정되면 메인의 백엔드 구현과 프런트 담당의 구현을 병렬 진행할 수 있다. 공유 파일은 메인 한 명이 작성한다.
6. 각 담당은 자기 변경 검증을 반환한다. 메인은 계약과 최종 diff를 확인하고 필요한 통합 검증을 수행한다.

## 지침 선택과 실제 적용 확인

선택 경로의 원본은 상위 `AGENTS.md`의 작업별 지침 표다. 상세 구조·검증 규칙은 각 저장소 문서에 유지한다.
상위 폴더에서 시작한 메인은 하위 지침·스킬이 자동 주입되었다고 가정하지 않고 표의 경로를 직접 읽는다.
스킬을 복제하거나 별도의 강제 주입 시스템을 추가하지 않는다.

다음 실제 버그 수정·기능 개선에서 아래를 확인한다. 이번 문서 수정은 해당 동작 검증을 대신하지 않는다.

- 시작: 선택한 지침·스킬과 선택 이유를 짧게 알린다. 관련 없는 문서는 로드하지 않는다.
- 구현: 변경 파일에서 관련 API·사용처·사용자 흐름까지 영향을 추적한다.
- 검증: 선택한 테스트와 제외한 검사의 이유, 실제 명령·결과를 남긴다. 공통 코드면 관련 사용처까지 넓힌다.
- 완료: 필요한 지침이나 검증 누락이 있었는지 확인하고, 실제로 확인한 문제만 원본 지침에 좁게 보완한다.

매 작업마다 별도 기록 파일을 만들지 않고 작업 보고에 포함한다. 백엔드만 바뀌고 화면 영향이 없으면 프런트 위임·E2E를 강제하지 않는다.

## 토큰 운영

전체 대화 상속을 끌 수 있는 실행 도구에서는 작업 요약만 전달한다. 지원되지 않으면 강제로 우회하지 않는다.
지침을 모두 매번 읽지 않고 대상 저장소 지침과 작업에 필요한 상세 문서만 읽는다.
같은 파일을 메인과 담당이 중복 분석하지 않도록 이미 확인한 파일·사실을 함께 전달한다.
성공한 검사는 새 변경·실패·미해결 우려가 없으면 반복하지 않는다.
역할 분리가 토큰 절감을 보장하지 않는다. 실제로 제공되는 총사용량, 실행 시간, 재작업을 기록해 단일 수행과 비교한다.
사용량이 제공되지 않으면 토큰 절감 수치를 추정해 보고하지 않는다.

## 설정 적용과 배포 범위

`.codex/agents/*.toml`은 공식 standalone custom-agent 형식을 사용한다. 모델은 부모 설정을 상속한다.
프로젝트 설정을 지원하고 신뢰하는 Codex에서 이 작업 폴더를 새 세션으로 열어 적용한다.
현재 세션의 도구에 커스텀 역할 선택 기능이 없으면 메인이 해당 역할 파일을 읽어 일반 서브에이전트에 지침으로 전달한다.
파일 생성만으로 현재 세션에서 에이전트 로딩·컨텍스트 격리가 확인된 것은 아니다.
소유 경로는 지침이며 OS 수준 접근 격리가 아니다. 권한·샌드박스는 부모 설정을 따른다.

상위 `ForTunCloud`를 통합 Git 저장소로 사용한다. 상위 AGENTS, .codex, harness와 두 프로젝트를 함께 관리한다.
기존 하위 `.git`의 이력 보존·정리는 사용자가 수행하며, 단순한 원격 연결만으로 통합이 완료된 것은 아니다.
각 프로젝트에는 자기 지침과 검증 스크립트를 유지한다. 기존 구성 보고서는 작성 당시 상태의 기록이다.
하위 저장소만 열면 상위 커스텀 에이전트 설정이 자동 로드된다고 가정하지 않는다.

## 현재 자동화 범위와 후속 작업

검증 스크립트는 기존 lint·타입·테스트·빌드를 연결한다. 구조 규칙은 현재 지침과 diff 검토로 확인한다.
자동 아키텍처 검사, HTTP 계약 테스트, 브라우저 E2E, 격리 테스트 DB, CI 연결은 아직 구현하지 않았다.
사용자가 테스트 DB를 준비했다. DB 테스트는 실제 테스트 연결·프로필·데이터 정리 설정을 확인한 뒤 실행한다.
유지보수·기능 개선에는 백엔드의 `forjun-maintenance` 스킬을 사용한다. 스킬은 검사 범위를 정하는 절차이며
없는 DB/API/브라우저 테스트를 자동으로 제공하는 것은 아니다. 문서·포맷 수정에는 적용하지 않는다.
후속 적용은 history의 작은 변경 → 계약 테스트 → 프로필 실패 복구 → 모듈 경계 검사 순으로 진행한다.
실제 서버 분리·스키마 변경·운영 배포는 개별 작업에서 범위와 복구 방법을 정한다.
