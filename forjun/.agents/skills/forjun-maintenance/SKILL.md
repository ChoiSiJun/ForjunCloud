# 유지보수·기능개선

백엔드 중심으로 요청을 구현하고, 변경 파일에서 영향을 받는 동작까지 추적해 필요한 검증을 수행한다.
프로젝트 구조·스타일 규칙은 이 문서에 복제하지 않고 저장소의 [AGENTS.md](../../../AGENTS.md)를 따른다.
이 스킬은 작업 절차이며 테스트 실행 도구나 테스트 코드 자체를 대신하지 않는다.

## 변경과 영향 범위 결정

- 버그라면 재현 조건과 기대 동작을, 개선이라면 기존/변경 동작과 완료 조건을 먼저 정한다.
- `git status`와 diff로 이번 작업 변경을 기존 사용자 변경과 구분한다. 커밋된 변경을 검증하는 요청은 요청된 커밋/범위를 사용한다.
- 관련 호출자·포트·매핑·API·DB 사용처를 검색한다. 파일 개수가 아니라 영향을 받는 기능으로 범위를 정한다.
- 변경 항목별로 영향 기능, 실행할 테스트, 선택 이유를 짧게 정리한다. 단순 작업은 별도 계획 파일을 만들지 않는다.
- 권한·JWT·예외 처리·공통 어댑터처럼 여러 기능이 쓰는 코드는 직접 수정한 모듈 밖의 관련 사용처도 검증한다.

## 구현과 테스트 선택

기존 구현·테스트 패턴을 따라 요청한 동작을 수정한다. 아래에서 필요한 검증을 조합한다.

| 변경 영향 | 기본 검증 | 추가 조건 |
| --- | --- | --- |
| Service 업무 판단·권한 | 관련 JUnit/Mockito 테스트 | 성공·거절·경계 조건 중 변경과 관련된 사례 |
| Entity·Repository·쿼리·트랜잭션 | 테스트 DB를 사용하는 관련 통합 테스트 | 저장/조회·매핑·롤백 등 변경이 보장해야 할 동작 |
| 경로·DTO·직렬화·인증·HTTP 오류 | 관련 API 테스트 | 상태 코드·실제 JSON·인증/소유권, 프런트 계약 영향 확인 |
| 화면 요청·응답 해석·사용자 흐름 | 위 백엔드 검사 + 관련 브라우저 E2E | 실제 조작과 최종 화면 결과 확인 |
| 공통 코드·스키마·여러 모듈 | 관련 사용처로 범위를 확대 | 선택 검사만으로 부족하면 전체 테스트와 추가 검증 |

- 기존 테스트가 변경 동작을 검증하면 재사용한다. 버그 회귀나 새 동작을 검증할 사례가 없으면 필요한 테스트를 추가한다.
- 구현을 그대로 복제하는 테스트나 영향 없는 낮은 위험 변경의 형식적 테스트는 추가하지 않는다.
- 화면에 영향 없는 내부 변경에는 브라우저 E2E를 강제하지 않는다. 반대로 UI 흐름이 바뀌면 백엔드 테스트만으로 E2E 완료를 주장하지 않는다.
- API 테스트가 MockMvc 기반인지 실제 서버 HTTP 요청인지 구분한다. MockMvc·DB 통합 테스트·빌드는 브라우저 E2E가 아니다.

## 실행

- 먼저 [검증 안내](../../../docs/harness/TESTING.md)를 읽어 현재 명령과 설정을 확인한다.
- 관련 테스트만 실행할 때 저장소 루트에서 Gradle Wrapper를 사용한다. 예:
  ` .\gradlew.bat --console=plain test --tests 'forjun.web.module.history.application.HistoryServiceTest' `
  클래스/메서드 선택자는 실제 존재하는 테스트로 지정하고 종료 코드와 현재 실행 보고서를 확인한다.
- DB 없는 기존 단위 테스트 묶음은 `powershell -NoProfile -File scripts/verify.ps1`로 실행한다.
  고정 목록이므로 새 테스트가 이 명령에 자동 포함된다고 가정하지 않는다.
- 사용자가 테스트 DB를 준비했다. DB 검사 전에 실제 테스트 전용 연결·활성 프로필·스키마 변경 설정·데이터 격리와 정리 방식을 확인한다.
  연결 정보가 저장소나 현재 환경에 없으면 비밀값을 출력하지 않고 필요한 설정만 요청한다. 기본 application 설정을 테스트 DB로 추정하지 않는다.
- HTTP/브라우저 요청의 서버 트랜잭션은 테스트 메서드의 롤백으로 정리된다고 가정하지 않는다.
  고유한 테스트 데이터와 실제 적용 가능한 정리 방법을 사용하고 공유 DB 전체 삭제는 하지 않는다.
- E2E는 기존 브라우저 테스트 도구·시나리오부터 찾는다. 가능하면 관련 자동 시나리오를 재사용하거나 추가한다.
  도구가 없으면 새 프레임워크 도입을 임의로 확대하지 않고, 사용 가능한 브라우저로 관련 흐름을 확인해 수동 검증으로 보고한다.
  브라우저 검증 자체가 불가능하면 미실행으로 보고한다.
- 프런트 변경이 필요하면 메인이 계약과 소유 파일을 정해 전달한다. 작은 변경 때문에 담당 에이전트를 추가 생성하지 않는다.
- 실패하면 재현 가능한 원인을 수정하고 영향받은 검사를 다시 실행한다. 환경 실패에 같은 명령을 무한 반복하지 않는다.
  기존 환경과 테스트가 갖춰진 범위는 끝까지 검증하고, 불가능한 항목은 원인과 필요한 설정을 남긴다.

## 완료 보고

- 수정한 동작과 변경 파일.
- 영향 범위 및 선택한 검증의 이유.
- 실제 명령, 종료 코드, 테스트 결과. 브라우저는 자동/수동 여부와 검사한 흐름.
- 제외한 검증과 이유, 코드 실패·환경 실패·미실행 항목.
- API 호환성·테스트 데이터 정리 결과 등 남은 영향.

이 스킬 추가만으로 DB 통합/API/E2E 테스트가 생기지는 않는다. 작업별로 존재 여부와 실행 증거를 확인한다.
